## Compare editions without inflating the result

When comparison is requested, preserve both editions and use matching format and viewport, with only one audible player. For verified identical narration/timing, use shared play/pause/seek/replay, explicit muting, drift correction and paired buffering; pause other comparison tabs. Reuse `software/comparison-player/sync.mjs` and its focused tests for that case. Browser synchronization is approximate, not a frame-locked composite.

Changed narration needs matching semantic passages on each take's own actual-audio timeline, at its native pace. Do not force wall-clock synchronization or stretch a performance to align pictures. Provide matched-loudness dry A/B listening so music and level differences do not confound the voice comparison. Generic labels are useful, but do not claim a genuinely blinded test when the mapping is available. Identify prior tempo processing and other differences that prevent an instruction-only causal comparison. Keep comparison pages and their own integrity manifest outside immutable delivery manifests.

Inspect the first frame, early payoff and representative mechanism, transition, caption and ending frames in both formats. `software/comparison_review.py EARLIER.mp4 LATEST.mp4 [--portrait]` supplies optional sampled RGB diagnostics; align timelines before interpreting them. Encoder noise, matching frame counts and image differences do not establish perceptual improvement. Separate changes to packaging, opening, core explanation, audio, accessibility and engineering evidence. State unchanged areas plainly; a fresh render is not a rewritten lesson. Tests, extra assets and more sampled frames never become a video-quality percentage.

Carry forward a meaningful subject at frame zero, one truthful focal idea in a dedicated small-readable cover, complementary accurate titles, staged comparisons, separated labels/captions and the quiet approved branding. Count *all* concurrent reading regions—including headings, supporting lines, diagram labels and captions—rather than praising a shorter heading while adding more text. Remove a supporting line when it merely repeats the headline, narration or picture. At narrow sizes, prioritize the mechanism and essential labels; do not add small annotations to manufacture novelty.

Distinguish a visible subject, an identity/outline reveal and an explanatory mechanism. An opening can improve orientation without improving the later lesson. Keep a genuine unanswered question where it helps curiosity. Brightness fades used to reveal an object must not imply that its physical illumination changed; label schematic conventions and prefer motion that represents the actual relationship. Do not require every topic to imitate the Moon technique.

Report a bounded editorial preference with reasons, not invented viewer testimony. If only the opening changed, prefer it provisionally for opening clarity and call the remaining explanation a tie when evidence supports that. Click appeal, retention, comprehension and willingness to return remain unmeasured until real observations exist. Record any specific new risk and its next smallest correction. Use the existing graphical/cognitive-load checks and one consolidated candidate decision; add no approval stage or mandatory audience study.

Every comparison must retain access to the delivered captions. When both landscape editions have identical narration/timing, one shared caption rail from the actual cues avoids duplication and keeps text outside the animations. Changed narration uses each take's own cue timing in separate landscape caption rails; keep timing tracks hidden so native captions cannot also overlay the picture. Serve those cue files on the comparison page's origin or verify the required cross-origin access. Keep the burned-in Shorts captions as delivered and omit duplicate native tracks. Preserve faststart/WebM recovery, seek, reopen and Replay behavior, and check that the complete portrait player and controls fit the intended viewport. Do not infer that external caption rails accompany an uploaded MP4. Preserve immutable media and store comparison UI separately.

## Optional review tooling: preflight the real runtime

Before installing a review tool, check existing availability and its full runtime requirements: downloads, expanded files, enforced first-boot storage, writable data, caches/snapshots and a safety reserve. Package size alone is not a fit test. Prefer isolated official binaries and pinned versions over package-manager operations that upgrade the production FFmpeg stack. Preview dependency changes, avoid unrelated tap-trust changes, and record any actual environment upgrade plus affected validation limits. Do not remove existing project files to fit optional tooling. Keep account/device state outside version control, and stop temporary connection services when a session ends. New access, purchases, binding licences and owner-only authentication retain their existing permission boundaries.

Verified example, scoped to the tested Google ARM64 emulator 37.2.13 and Android 11 Play Store image: the packages expanded to 4.17 GB, but first boot enforced a 6 GiB userdata minimum and 1.2 free-space factor (7372.80 MiB). The documented smaller-partition option did not override it. The attempted setup therefore remained unbooted; it supplied no Instagram caption evidence. See [Google emulator source](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-32-release/android-qemu2-glue/main.cpp). Recheck actual versions rather than making these historical numbers a universal default. Correct an optimistic readiness statement promptly; do not bypass the runtime check or claim that installation proves successful review. Optional tooling is not a new release gate.
